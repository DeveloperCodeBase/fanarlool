# معماری سامانه و تصمیم های فنی

دموی محصول: [https://fanarlool.vistapower.ir](https://fanarlool.vistapower.ir)

شناسه: FL-SW-04 | نسخه ۲.۰ | تاریخ تدوین: ۱۴۰۵/۰۷/۱۲ | وضعیت: نسخه نخست محصول؛ هسته نرم‌افزاری عملیاتی در محیط تولید و برنامه تکمیل صنعتی

## مسیر درخواست

مرورگر ← HTTPS روی Caddy موجود ← Nginx موجود روی ۸۰۸۰ ← فایل‌های dist یا مسیر /api/ ← سوکت /run/fanarlool/api.sock ← سرویس Node ← SQLite در shared/data. افزودن API هیچ listener TCP جدیدی ایجاد نمی‌کند.

## ADR-01 احراز هویت واقعی

نیاز جدید به سطح دسترسی سازمانی با انتخاب نمایشی نقش حل نمی‌شود. backend اختصاصی حداقلی افزوده شد. حساب، مجوز، نشست، تأیید و اعتبارسنجی روی سرور اعمال می‌شوند؛ فرانت فقط نمایش و دریافت ورودی را انجام می‌دهد.

## ADR-02 ذخیره پایدار

SQLite با WAL برای پایلوت تک‌سروری و هزینه محدود انتخاب شده است. مهاجرت به PostgreSQL پس از نیاز به چند سرور، بار نوشتن بالا یا HA تصمیم بعدی است. API node:sqlite در Node 22 وضعیت آزمایشی دارد؛ نسخه runtime باید پین و تغییر آن در گیت بررسی شود.

## ADR-03 تفکیک عملیات و نمایش

ماژول‌های شبیه‌سازی به صورت lazy بارگذاری می‌شوند. داده تصادفی وارد سوابق عملیاتی و گزارش صندوق نمی‌شود. اتصال صنعتی در لایه جمع‌آوری جدا توسعه می‌یابد و هیچ فرمان کنترلی به PLC در نسخه حاضر وجود ندارد.

## ADR-04 استقرار کم تداخل

build روی VPS از commit دقیق، کنترل manifest و تعویض اتمی symlink. Caddy و Nginx مشترک حفظ می‌شوند؛ فقط virtual host اختصاصی و واحد fanarlool-api تغییر می‌کنند. rollback کد با rollback داده یکی نیست.

## مرز اعتماد و مسیر اطلاعات

مرز ۱: اینترنت تا Caddy با TLS. مرز ۲: proxy مشترک تا virtual host اختصاصی با کنترل مسیر. مرز ۳: Nginx تا سوکت اختصاصی با مجوز گروه. مرز ۴: API تا دیتابیس خصوصی با SQL آماده و تراکنش. مرز ۵ توسعه: شبکه OT تا جمع‌آورنده LAN با least privilege و جریان read-only. داده نمایش، نمونه دمو و رخداد واقعی در قراردادهای جدا مدیریت می‌شوند. افشای log خام میزبان از پنل وب در دامنه نیست.

## تصمیم دمو و ظرفیت

هر فضای دمو SQLite در حافظه مستقل دارد؛ cookie فضای نمونه و cookie نشست آن به حساب واقعی ارتباطی ندارند. ۲۴ فضای همزمان، ۲۰۰ رکورد و ۳۲ نشست در هر فضا سقف فعلی‌اند؛ audit آموزشی به حدود هزار رخداد محدود می‌شود. بیکاری یک ساعت یا restart موجب خاتمه داده نمونه است. برای بار بالاتر، sandbox pool جدا از فرایند production با TTL و budget مستقل پیشنهاد می‌شود.

## تفکیک لایه سند و اجرای کارخانه

دفتر records، گردش ثبت و تأیید سند را پوشش می‌دهد. اجرای کارخانه، سفارش، بچ، کار و حرکت موجودی را با قواعد تخصصی اداره می‌کند؛ approved شدن سند به تنهایی release شدن سفارش یا بچ نیست. تحلیل بازه از مجموعه مجاز و کامل سرور استخراج می‌شود و جدول رابط تنها یک صفحه از آن مجموعه است. داده ارزیابی از دفتر عملیاتی جدا می‌ماند. قرارداد هر دو لایه باید منبع، مجوز، نسخه و رخداد مرتبط را حفظ کند؛ اتصال ERP یا PLC به صورت خودکار از این روابط استنباط نمی‌شود.

## دوقلوی مهندسی، حساب و مشاهده‌پذیری — schema۴

ماژول server/twin.mjs مدل compression-spring-wahl-v1 را با G و تنش مجاز صریح اجرا می‌کند. مرجع تجهیز/دستور ساخت باید تأییدشده باشد. سناریو و baseline هندسی snapshot با نسخه مرجع ذخیره می‌شوند؛ نیرو و خواص ماده در مقایسه به هر دو حالت اعمال می‌شوند. تغییر نسخه یا وضعیت تأیید مرجع، preview اصلاحی و PATCH را با 409 متوقف می‌کند؛ GET تاریخچه را حفظ می‌کند. خروجی ۲۱ نقطه نیرو–خیز، تماس حلقه، تنش Wahl و مقایسه عددی دارد. این مدل اتصال زنده OT، مدل خستگی یا تغییر خودکار دستور ساخت نیست.

ماژول account-services.mjs پروفایل نسخه‌دار و خلاصه مجاز شخصی را ارائه می‌کند. نقش، شناسه و رمز از PATCH پروفایل قابل تغییر نیستند. اطلاعات واحد/سمت/شیفت خوداظهاری هستند. مانیتور admin شامل ring محدود ۵۰۰ درخواست، صفحه‌بندی SQL audit و نشست‌های گروه‌بندی‌شده بدون توکن است؛ شمارنده buffer برابر SLA تاریخی نیست. quick_check هر پنج دقیقه برای همان DatabaseSync cache می‌شود؛ health.checkedAt زمان بررسی اصلی و generatedAt زمان مشاهده است. حافظه، فرآیند اختصاصی شامل فضاهای ارزیابی را اندازه می‌گیرد.
